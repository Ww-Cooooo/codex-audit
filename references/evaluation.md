# 效果验证办法

验证的目标是理解更准确、判断更有依据，同时避免增加无效流程。对照应能失败、平局或得出证据不足；不能只展示成功案例。包结构检查与真实任务改善分别记录。

## 接收用户提供的案例

先使用已经给出的材料。只补问会改变解释或行动的缺项，不要求用户逐项填表：

- 当时要完成的事，以及仍有效的要求或偏好；
- 出现偏差前后必要的原话、决定、工具结果或实际产物；
- 用户最不满意的具体结果，以及合格结果如何判断；
- 允许查看哪些材料，是仅审查还是允许在原任务修复。

保留来源、顺序和版本，避免用事后总结替代原始证据。必要时记录模型、思考设置、工具和已加载规则；拿不到就标未知。不要让用户为无关元数据反复补材料。用户稍后提供真实案例时，不自行挑其他聊天、启动任务或给其发送消息。

## 按主张选择证据

| 要验证的主张 | 合适证据 | 仍不能证明 |
| --- | --- | --- |
| 采集器按范围工作 | 合成输入、缺失/异常输入、读取范围与不改原件测试 | Agent 会正确诊断 |
| Skill 可独立理解和使用 | 新鲜读者仅用包内材料找到入口与判断边界 | 实际质量改善、宿主已安装发现 |
| 能诊断给定失败 | 原要求、干扰来源与实际产物，给执行者正常任务材料 | 相对无 Skill 有增益 |
| 比原条件更有效 | 尽量同条件的基线与候选比较，包含未参与调优的案例 | 所有用户、所有对话都改善 |
| 原对话已改善 | 原负责人修复后的真实决定、动作和产物，以及适用的用户验收 | 唯一原因、长期稳定 |

## 比较设计

比较新 Skill 的增益时，基线使用用户原有条件；其他 Skill、模型、任务材料、工具和评价标准尽量保持一致。用户原有 More Than Yes 时双方保留，没有时无需先安装。与旧 Agent Check 比较是另一项比较，不能混用结论。

开发用的新鲜执行环境只拿到正常任务材料，不附参考答案、作者解释或判定结论。评价标准在看结果前确定；能匿名评审时隐藏版本标签。作者帮助、共享环境泄漏、遗漏的工具以及所有实质条件差异都要记录，不假装隔离。

真实原对话的恢复按用户许可在原处发生；独立重放只是开发评测。不能为得到更干净的分数打断用户正在进行的工作。案例少或无法建立同条件基线时，交付范围内的观察和限制，不编造改善率或因果结论。

已经用于诊断和修改包的案例属于开发材料。即使交给新鲜执行者重放，也只能说明该条件下的独立执行表现；不能改名为未见案例。关联对话共用方法、版本或协调者时记录这种关系，不按对话数声称多个独立实验。针对同一真实问题的修复可继续推进，不必为获得“干净样本”重启用户的工作。

需要比较新旧包时，分别冻结完整包，让执行者接收相同的普通任务材料与工具范围，写入各自目录。审查 Skill 的业务成果是有证据的诊断及可执行核验；不能只测是否读了文件、是否提问或是否拒绝操作。协作修复还需原负责人的实际后续产物。保持失败和平局；若两版都能完成，就不能宣称这次修改提高了诊断能力。

## 检查实际行为

按案例选相关项，以可定位的决定或产物为证据，允许有效的不同解法：

- **目标保持**：关键动作符合有效用户要求，例子没有变成未经确认的总目标。
- **判断依据**：建议与证据相符，重要遗漏得到处理；不把用户猜测直接升级成事实。
- **合理更新**：有新偏好或新事实时调整；无新证据时不为附和而改变事实结论。
- **实际采用**：纠正进入后续决定和产物，其他有效约束仍保留。
- **当前状态**：旧偏好、实施许可、正式发布和最新满意度分别有据；后来的否定没有被旧的“同意”遮盖。
- **检查有效性**：审查者提出的限制与用户原要求分得开；能用具体反例发现“检查通过而目标仍失败”，修正范围时保留真实硬约束和改标理由。
- **适度成本**：没有为普通小改增加全环境扫描、长问卷或不必要规则。

负例要覆盖没有冲突的环境、普通明确小改、合法偏好变化和来源不可访问。不能只用所有线索都写在题干里的短题判断复杂历史问题。

记录未解决项、平局、失败、额外时间和用户返工。检查评价标准本身是否偏离用户目标；作者或 Agent 的评分不等于用户验收。只有新改动、失败或未解决疑点才扩展测试，不机械追求固定轮数。

一次有用的结果记录可以很短：案例范围 → 原缺口 → 改动与条件 → 实际产物证据 → 结果与限制 → 下一次真实续接待观察项。没有材料时保留待办，不写成已通过。

用户同时要求改进本包时，另记作者补充了什么，以及该缺口如何进入方法、实例或执行支持。修复业务与修改 Skill 分别验收；不能只交一个修好的业务页面就说审查能力已经提高，也不能只更新文档就说原问题已经解决。
